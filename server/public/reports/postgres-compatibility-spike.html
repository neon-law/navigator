Failure injection and limits

The synthetic controller waits for a committed business write, then SIGKILLs the DBOS/Axum process before the step checkpoint. A non-idempotent attempts table records two executions of that step, while its unique-key effect table has one business effect. The previously completed step runs once. Recovered status is SUCCESS, with recovery_attempts 2 in the observed run. Extension rows and the AGE graph survive a PostgreSQL restart.

For a real multi-row business operation, commit its unique replay key, result, domain writes and any outbox rows in one PostgreSQL transaction. A replay reads the stored result and skips the write. Serialize conflicting state transitions with a row lock or compare-and-swap version; a reused key with different input must be rejected. Retry SQL serialization/deadlock failures within bounded application policy. Provider calls need stable idempotency keys or explicit reconciliation: an outbox alone does not prevent a duplicate remote effect after acknowledgment loss.

Rust 1.98 formatting and Clippy checks passed; navigator validate passed with zero errors. The test proves completed checkpoint replay and the business-write/checkpoint window. It does not prove interrupted durable sleep, signals, actor attribution, ephemeral workflows, queue concurrency, rolling versions, graceful Axum drain, database/host crash recovery, PITR, operator compatibility or extension upgrades. These remain ENG-990/ENG-1022 acceptance gates. DBOS is an application dependency; the database image contains no DBOS executor.

Decision and first milestone

First build one reproducible PostgreSQL compatibility image and CI smoke lane. It must install PostgreSQL, DBOS’s tested server prerequisites, Apache AGE, citext, pgvector, and the selected full-text-search support. That image becomes the local and CI contract. Then rerun the DBOS recovery and AGE/API parity checks on it before choosing the application SQL and migration libraries.

Keep

DBOS native Rust for durable workflows; Axum for HTTP; PostgreSQL as the application store; Firm → Brand → Project tenancy; project-scoped documents with an Active Storage-like metadata/blob split; full database snapshots to Iceberg at 05:55 and 17:55 UTC.

Remaining decisions

The exact compatibility tuple is pinned above. Select one Rust SQL client; one Rails-style timestamp migration runner; extension upgrade policy; graph projection/event-log contract; and production archive catalog and retention.

Release boundary

Public source moves to Apache-2.0 only after license and dependency review, file/asset audit, CI proof, and the requested fresh public-source commit. Navigator first-party source is Apache-2.0. Upstream components and assets retain their own licenses; redistribution still requires dependency, notice, and ownership review.

Rails-style migration convention

Use ordered timestamp filenames with a migration ledger, for example 20261010120000_create_firms.sql. A Rust migration runner should sort filenames, checksum applied files, take a PostgreSQL advisory lock, and record version, name, checksum, start/finish, and success. This spike does not select the runner or SQL client. Reversible DDL is preferred; data migrations should be bounded, restartable batches with explicit validation and rollback limits.

db/migrate/
  20261010120000_create_firms.sql
  20261010120500_create_brands.sql
  20261010121000_create_projects.sql
  20261010121500_add_project_scope_to_assets.sql
  20261010122000_create_relationship_log.sql
  20261010122500_enable_search_extensions.sql

Sequence dependencies explicitly: PostgreSQL roles/database/schema and extensions → DBOS-owned system migrations in its dedicated schema → Navigator timestamp migrations → compatibility views/triggers and dual-write → reconciliation/read shadowing → cutover → stop old writes → later Surreal retirement. DBOS's Config::migrate is distinct: it manages DBOS internal tables. For a centrally controlled schema rollout, set it false and run SDK migrations in a dedicated deploy job only after upstream documents that workflow; otherwise allow DBOS to migrate only inside its isolated schema.

Test a fresh database, upgrade from every released migration boundary, rerun idempotent data jobs, interrupted DDL/data migration, checksum drift, two concurrent migrators, extension update, downgrade procedure, and restore from backup. Timestamp names are a human ordering convention; the ledger enforces exactly-once application.

Nightly Iceberg archive contract

Retain Kubernetes CronJob scheduling and use DBOS for durable execution. Each nightly run snapshots the transactionally consistent state of every eligible application table and records an Iceberg snapshot in the separate GCP archive bucket. Staging and production must have distinct top-level prefixes and catalog namespaces.

gs://<separate-neon-log-archives-bucket>/
  staging/application/<table>/...   staging/dbos/<table>/...
  staging/graph/<graph>/...        staging/telemetry/<signal>/...
  production/application/<table>/... production/dbos/<table>/...
  production/graph/<graph>/...      production/telemetry/<signal>/...

“Everything” requires an explicit source inventory: app schemas, DBOS queue/journal/status/event tables, AGE graph labels and catalog metadata, and required telemetry. Define a consistent cross-table cutoff, row-level error reporting, incremental-vs-full snapshot cadence, tombstone/deletion capture, restore drills, encryption/IAM, retention, legal holds, and separation between archive writers and downstream readers before broad access.

Suggested issue sequence

  1. Pin contracts. Choose Postgres major, AGE/pgvector/DBOS versions; map platform support; define tenant and UUID/timestamp contracts. This is ENG-990 and its blockers.
  2. Build the image. Separate source repo, reproducible Docker build, SBOM/license/security checks, GHCR or other registry decision, digest pinning, CI service and local KIND integration.
  3. Prove extensions and SDK. Run DBOS migrations/workflow/recovery, AGE traversal/projection, citext, vector, FTS, backup/restore in CI using the published image.
  4. Land SQL foundation. Pick sqlx or tokio-postgres; Rails-like timestamp migration runner and ledger; typed rows and UUIDv4/timestamptz; dual database and dual-write failure model.
  5. Translate by bounded domains. Begin with a low-risk reference table and tenant-level integration tests; then firms/brands/projects, assets, graph/relationship logs, durable workflows, and remaining Store modules. Keep reads shadowed and compare before cutover.
  6. Export and cut over. Add separate staging/prod Iceberg archives and prove restore; shadow reads; reconcile row counts, permissions, relations, documents and workflows; cut over writes; retain rollback until accepted; decommission Surreal only after parity.
  7. Open-source release. Resolve third-party dependency/license boundaries, code ownership, trademarks, secrets/assets, NOTICE/SBOM and contributor policy; create the fresh public commit and publish after all gates.

Compatibility test gates

Database and image

  • Fresh init and upgrade tests on the exact image digest.
  • All required extensions load; version and ABI checks pass.
  • Database image upgrade and PITR/backup restore preserve app, DBOS, AGE, and Iceberg references.
  • Concurrent migration lock, checksum drift, interrupted migration and recovery tests.

Tenant/API parity

  • Capture the current API/OpenAPI route/method/status/request/response inventory before edits.
  • Run the same contract suite against Surreal and Postgres adapters during dual-write.
  • Firm/Brand/Project scoping, role authorization, uniqueness, nullability, sort order, soft delete and error semantics match.
  • Every table and API has owner, test, docs, migration and cutover status in the inventory.

Workflows and relationships

  • Golden workflow specs produce the same state and event history through InMemory and DBOS adapters.
  • Crash at every external effect/checkpoint boundary; retries remain safe with durable keys.
  • Actor attribution, ephemeral workflows, queue backpressure, wakeups, timers, version rollouts and cancellation pass.
  • Rebuild AGE graph from canonical rows/logs and compare all traversals under tenant filters.

Archives and search

  • Every source table/graph/system table appears in manifest inventory or an explicit exclusion.
  • Snapshot manifests carry source, environment, cutoff, schema/migration and row-count metadata.
  • Restore a nightly staging archive into an isolated test project; verify parity and access boundaries.
  • Search result fixtures prove tokenization, language, ranking, fuzzy behavior and project filtering.
